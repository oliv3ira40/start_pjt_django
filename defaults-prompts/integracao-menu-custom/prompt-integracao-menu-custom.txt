# PROMPT 1 — Integrar o layout aprovado do novo cabeçalho e menu lateral

## Objetivo

Integrar ao Django Admin do Colmeias Online o layout aprovado no arquivo:

`n-colmeias-online-menu-lateral.html`

Esta primeira etapa é exclusivamente de **integração visual e estrutural**.

O objetivo é substituir a apresentação atual do cabeçalho e do menu lateral pelo design criado no DevFront, preparando corretamente os templates, partials, classes, assets e pontos de integração que serão funcionalizados na etapa seguinte.

Não redesenhar o layout e não criar uma nova proposta visual.

## Fonte visual obrigatória

Utilizar como fonte principal o arquivo:

`n-colmeias-online-menu-lateral.html`

Trabalhar exatamente sobre a versão mais recente disponível na área de layouts do projeto, incluindo os ajustes aprovados posteriormente:

* mesma marcação visual para item avulso ativo e grupo com submenu ativo;
* fundo ativo corretamente centralizado;
* ícones alinhados no menu expandido e minimizado;
* animações e espaçamentos definidos no arquivo;
* cabeçalho e menu formando uma única estrutura visual;
* versão mobile em formato de drawer.

Não utilizar versões anteriores ou protótipos rejeitados.

## Auditoria inicial

Antes de modificar:

* ler integralmente o `AGENTS.md`;
* localizar o arquivo aprovado;
* auditar a herança atual dos templates do Django Admin;
* identificar o template base do Admin;
* localizar o cabeçalho atual;
* localizar o menu nativo do Django;
* localizar a implementação do `admin_menu`;
* identificar os CSS e JavaScript globais atualmente carregados;
* identificar como páginas CRUD e páginas customizadas herdam a estrutura;
* verificar o comportamento atual para usuário comum, superusuário e fallback;
* localizar os arquivos oficiais de logo e símbolo em `core/static/identidade-visual/`.

Não presumir que alterar apenas um template será suficiente. Auditar todos os consumidores da estrutura global.

## Escopo desta etapa

Implementar a estrutura visual de:

* cabeçalho desktop;
* cabeçalho mobile;
* menu lateral expandido;
* menu lateral minimizado;
* contêiner destinado à expansão temporária;
* área de busca;
* itens avulsos;
* grupos com submenus;
* itens inferiores;
* backdrop mobile;
* drawer mobile;
* área principal de conteúdo.

Nesta etapa, preparar os elementos e hooks necessários para as funcionalidades futuras, mas não implementar ainda toda a lógica de interação descrita no protótipo.

## Integração com o Django Admin

Transformar a estrutura do DevFront em componentes reutilizáveis do Admin.

Preferir uma organização adequada à arquitetura existente, como:

* template base ou override do Admin;
* partial do cabeçalho;
* partial do menu lateral;
* partial de item avulso;
* partial de grupo e submenu;
* arquivos CSS próprios;
* arquivo JavaScript preparado para a etapa seguinte.

Não copiar o HTML completo do protótipo para todas as páginas.

Não duplicar cabeçalho e menu em cada template.

O conteúdo real das páginas deve continuar sendo renderizado pelos blocos atuais do Django Admin.

## Conteúdo real do menu

Não transportar para o Django os itens demonstrativos hardcoded do DevFront como fonte definitiva.

A estrutura visual deve ser alimentada pelo mecanismo real já existente no `admin_menu`.

Nesta primeira etapa:

* manter os itens reais configurados no sistema;
* manter a ordem real;
* manter grupos e submenus reais;
* manter itens avulsos;
* manter as permissões atuais;
* preservar os links atuais;
* preservar o fallback existente;
* não modificar seeds;
* não criar novos registros de menu;
* não reorganizar funcionalidades.

O arquivo do DevFront define a apresentação, não a fonte dos dados.

## Cabeçalho

Integrar o cabeçalho aprovado.

### Lado esquerdo

Preparar:

* botão de abrir o menu no mobile;
* área da identidade visual;
* logo horizontal oficial no estado apropriado;
* símbolo oficial no estado apropriado;
* controle de minimizar ou expandir no desktop.

Utilizar somente os arquivos oficiais existentes.

Não:

* redesenhar a logo;
* recriar a logo em SVG manual;
* recolorir;
* usar versões demonstrativas do protótipo;
* distorcer as proporções.

### Lado direito

Exibir apenas:

* saudação ao usuário;
* `Ir para o site`;
* `Encerrar sessão`.

Não incluir:

* Alterar senha;
* modo escuro;
* seletor de tema;
* notificações;
* configurações;
* avatar obrigatório;
* outras ações do Django Admin.

Nesta primeira etapa, preservar os destinos atuais quando eles já existirem. A ligação definitiva e a validação dos fluxos serão feitas no segundo prompt.

## Logo expandida e símbolo

Preparar dois estados visuais:

### Menu expandido

Exibir a versão horizontal completa da identidade do Colmeias Online.

### Menu minimizado

Exibir apenas o símbolo oficial, mantendo alinhamento e área de proteção.

Não deixar as duas versões visíveis simultaneamente.

Não permitir sobreposição, compressão ou resíduo visual durante a mudança de estado.

## Menu lateral

Integrar visualmente:

* busca;
* itens avulsos;
* grupos;
* submenus;
* indicação de item ativo;
* indicação de grupo que contém item ativo;
* área inferior;
* ícones;
* setas;
* tooltips;
* estados expandido e minimizado.

Manter exatamente o padrão visual aprovado:

* item avulso ativo e grupo ativo com a mesma marcação;
* fundo claro arredondado;
* barra dourada lateral;
* ícone centralizado;
* ausência da antiga bolinha dourada;
* mesma coluna de alinhamento para todos os ícones.

## Conteúdo principal

O novo shell não pode alterar os layouts internos das páginas.

Preservar:

* formulários;
* tabelas;
* mensagens;
* breadcrumbs quando realmente utilizados;
* títulos customizados;
* modais;
* páginas customizadas;
* assets específicos;
* validações;
* páginas CRUD do Admin.

Não adicionar ao conteúdo:

* `max-width` global;
* background decorativo;
* padding duplicado;
* margem adicional desnecessária;
* card externo envolvendo todas as páginas.

O conteúdo deve continuar utilizando toda a largura disponível ao lado do menu.

## Responsividade estrutural

Preparar a estrutura para os estados previstos.

### Desktop

* cabeçalho no topo;
* menu abaixo do cabeçalho;
* conteúdo ao lado;
* estado expandido como padrão inicial;
* estado minimizado disponível por classe;
* contêiner preparado para sobreposição temporária.

### Mobile

* cabeçalho compacto;
* menu fora da viewport quando fechado;
* drawer preparado para abrir pela esquerda;
* backdrop preparado;
* conteúdo ocupando toda a largura;
* nenhuma reserva permanente de espaço para o menu;
* uso correto de `100dvh`;
* consideração das áreas seguras do iPhone.

Nesta etapa, é aceitável manter apenas o comportamento atual indispensável para não bloquear a navegação. As interações definitivas serão implementadas no segundo prompt.

## CSS

Adaptar o CSS do DevFront para assets reais do projeto.

Garantir:

* isolamento por classes específicas do shell do Admin;
* ausência de regras genéricas para todos os botões, links, inputs ou headers;
* ausência de conflito com CSS das páginas customizadas;
* ausência de conflito com componentes de select, PhotoSwipe, galerias, modais ou formulários;
* ausência de rolagem horizontal;
* z-index organizado;
* respeito a `hidden`;
* respeito a `prefers-reduced-motion`.

Remover do CSS importado:

* estilos destinados apenas aos cards demonstrativos;
* conteúdo fictício;
* fundo da página de demonstração;
* regras usadas apenas para simular a área principal;
* ajustes que interfiram nos layouts reais.

## JavaScript nesta etapa

Não transportar automaticamente todo o JavaScript demonstrativo.

Nesta primeira fase:

* preparar seletores e atributos `data-*`;
* preservar somente o necessário para o layout não quebrar;
* não implementar ainda busca completa;
* não implementar persistência;
* não implementar ainda expansão temporária definitiva;
* não criar lógica duplicada em relação ao menu atual;
* não transportar arrays ou dados fictícios;
* não usar URLs hardcoded.

O código definitivo de interação pertence ao segundo prompt.

## Preservação obrigatória

Não alterar:

* models;
* migrations;
* permissões;
* ownership;
* `ScreenAccessMiddleware`;
* regras de visibilidade;
* registros do menu;
* seed do menu;
* rotas existentes;
* páginas públicas;
* conteúdo das páginas internas;
* PWA;
* autenticação;
* comportamento de logout;
* regras específicas de superusuário;
* fallback atual do menu.

O novo layout deve respeitar o escopo em que o menu customizado já é aplicado.

## Testes

Adicionar ou atualizar testes compatíveis com esta etapa para validar:

* renderização do novo cabeçalho;
* renderização do novo menu;
* ausência do menu nativo duplicado no escopo customizado;
* presença da logo oficial;
* presença do símbolo oficial;
* presença apenas de `Ir para o site` e `Encerrar sessão`;
* conteúdo principal continua renderizado;

Executar também:

* testes de renderização dos templates base;
* `python3 manage.py check`.

## Critérios de aceite

* O layout visual de `n-colmeias-online-menu-lateral.html` foi integrado ao Admin.
* O layout não foi redesenhado.
* O cabeçalho utiliza os assets oficiais.

# PROMPT 2 — Tornar funcional o novo cabeçalho e menu lateral

## Objetivo

Após a conclusão e validação da integração visual, tornar completamente funcional o novo cabeçalho e menu lateral implementados a partir de:

`n-colmeias-online-menu-lateral.html`

Trabalhar sobre a implementação produzida no primeiro prompt.

Não refazer templates, não redesenhar o componente e não substituir o layout aprovado.

Esta etapa deve conectar ao sistema real:

* links;
* grupos;
* busca;
* estado ativo;
* minimização;
* expansão temporária;
* drawer mobile;
* logo;
* saudação;
* logout;
* acessibilidade;
* preservação de estado quando aplicável.

## Auditoria inicial

Antes de alterar:

* ler integralmente o `AGENTS.md`;
* revisar a entrega do primeiro prompt;
* comparar novamente com o arquivo do DevFront;
* auditar a implementação real do `admin_menu`;
* verificar o contexto já enviado aos templates;
* identificar todas as rotas nomeadas;
* identificar o fluxo nativo de logout;
* identificar a rota real da Home pública;
* identificar a rota de Minhas assinaturas;
* identificar `admin:delete_personal_data`;
* verificar a lógica atual de item ativo;
* verificar o fallback para o menu nativo;
* verificar se já existe persistência aprovada para estado do menu.

## Dados e segurança

O menu deve continuar sendo alimentado exclusivamente pelo backend atual.

Não confiar em listas ou permissões definidas no JavaScript.

O frontend pode:

* abrir;
* fechar;
* filtrar visualmente;
* destacar;
* minimizar;
* expandir.

O frontend não pode decidir quais itens o usuário tem permissão para acessar.

Preservar:

* visibilidade configurada;
* permissões;
* `ScreenAccessMiddleware`;
* ownership;
* escopo para usuário comum;
* comportamento de superusuário;
* fallback seguro em caso de falha.

## Header funcional

### Saudação

Exibir o usuário autenticado real.

Usar a apresentação já adotada pelo projeto, sem expor informações desnecessárias.

Exemplo visual:

`Bem-vindo, Augusto`

Não hardcodar nome.

### Ir para o site

Conectar à rota nomeada real da página pública principal.

Não usar `/` hardcoded sem auditar a rota oficial.

### Encerrar sessão

Manter o fluxo nativo e seguro de logout do Django.

Se a versão atual exigir POST:

* usar formulário com CSRF;
* apresentar visualmente como link administrativo;
* não trocar por GET apenas para simplificar.

Não criar uma página ou endpoint paralelo de logout.

## Logo conforme o estado

### Desktop expandido

Exibir a logo horizontal oficial.

### Desktop minimizado

Exibir somente o símbolo oficial.

### Expansão temporária

Ao expandir temporariamente o menu minimizado, apresentar a versão prevista no layout sem:

* piscar;
* sobrepor;
* exibir as duas marcas;
* comprimir a logo;
* provocar mudança permanente do estado.

### Mobile

Usar a versão aprovada para o cabeçalho e drawer mobile.

## Grupos e submenus

Tornar funcionais todos os grupos reais.

Garantir:

* toda a linha do grupo clicável;
* múltiplos grupos abertos simultaneamente;
* seta atualizada;
* `aria-expanded`;
* `aria-controls`;
* animação entre 220 e 300 milissegundos;
* nenhum salto visual;
* nenhum terceiro nível;
* grupo contendo item ativo aberto inicialmente;
* item ativo preservado mesmo se o usuário fechar o grupo manualmente.

Os links finais devem usar as URLs resolvidas no backend.

## Estado ativo

Identificar a página atual principalmente por:

`resolver_match.view_name`

Não usar prefixo textual da URL como regra geral.

Aplicar corretamente:

* item avulso ativo;
* submenu ativo;
* grupo pai contendo submenu ativo;
* página customizada sob `/admin/`;
* CRUDs do Admin.

Preservar a marcação visual unificada aprovada:

* fundo claro;
* barra dourada lateral;
* ícone alinhado;
* sem bolinha diferente para item avulso.

## Busca

Implementar o filtro do menu.

A busca deve:

* filtrar itens avulsos;
* filtrar grupos;
* filtrar submenus;
* ignorar maiúsculas, minúsculas e acentuação quando possível;
* atualizar durante a digitação;
* manter o grupo pai visível quando um submenu corresponder;
* abrir temporariamente os grupos com resultados;
* exibir `Nenhum item encontrado.` quando necessário.

Ao iniciar uma busca:

* guardar em memória os grupos que estavam abertos;
* não alterar permanentemente a preferência do usuário.

Ao limpar:

* restaurar os itens;
* restaurar os grupos que estavam abertos antes da busca;
* remover o estado de nenhum resultado.

Não enviar consulta ao backend.

## Desktop expandido e minimizado

### Minimizar

Ao clicar no controle:

* reduzir o menu para a largura aprovada;
* ocultar textos completamente;
* ocultar a busca completa;
* manter os ícones;
* manter o estado ativo;
* reajustar permanentemente a área do conteúdo;
* trocar a logo completa pelo símbolo;
* não deixar resíduos visuais.

### Expandir permanentemente

Ao clicar novamente:

* restaurar o menu completo;
* restaurar logo horizontal;
* restaurar textos;
* restaurar busca;
* restaurar grupos;
* reajustar a área do conteúdo.

A animação deve seguir aproximadamente 260 a 340 milissegundos.

## Expansão temporária por hover

Quando o menu estiver permanentemente minimizado:

* iniciar a expansão ao entrar na área real do menu;
* usar pequeno atraso de abertura;
* expandir sobre o conteúdo;
* não deslocar o conteúdo;
* não mudar a preferência permanente;
* recolher ao sair da área visual real.

Utilizar aproximadamente:

* abertura: 100 a 180 milissegundos;
* fechamento: 140 a 220 milissegundos.

Cancelar corretamente os timers quando o cursor retornar.

Não criar uma zona invisível maior que o menu.

Não obrigar o usuário a afastar muito o cursor.

## Expansão por foco

Quando o menu estiver minimizado e um item receber foco pelo teclado:

* expandir temporariamente;
* manter aberto enquanto o foco estiver dentro;
* recolher quando o foco sair;
* não depender de hover.

## Tooltips

No estado minimizado e não expandido temporariamente:

* mostrar tooltip para cada item;
* funcionar por hover e foco;
* usar o título real;
* não ser cortado;
* não aparecer junto ao menu temporariamente aberto;
* não bloquear cliques.

## Mobile

No mobile, o menu deve iniciar fechado.

Ao clicar no botão do cabeçalho:

* abrir o drawer pela esquerda;
* exibir backdrop;
* bloquear o scroll da página;
* preservar a posição do scroll;
* mover o foco para o drawer;
* manter busca, grupos e itens inferiores acessíveis.

O drawer deve:

* usar `100dvh`;
* respeitar safe areas;
* possuir rolagem interna;
* não gerar rolagem horizontal;
* manter o botão de fechar visível;
* deixar uma faixa de backdrop à direita.

## Fechamento mobile

Fechar por:

* botão de fechar;
* backdrop;
* tecla Escape;
* clique em link final.

Não fechar ao:

* abrir grupo;
* fechar grupo;
* focar busca;
* limpar busca.

Ao fechar:

* restaurar o scroll;
* restaurar a posição da página;
* remover classes temporárias;
* devolver foco ao botão de abertura.

## Itens inferiores

Conectar corretamente:

* Minhas assinaturas;
* Meus dados e privacidade.

`Meus dados e privacidade` deve reutilizar:

`admin:delete_personal_data`

Não criar nova tela.

Minhas assinaturas deve utilizar a integração e rota real já existentes.

Os dois continuam como itens avulsos fora de grupos artificiais.

## Persistência de estado

Persistir somente os estados aprovados e realmente necessários:

* menu permanentemente expandido ou minimizado;
* grupos abertos.

Não persistir:

* expansão temporária;
* busca digitada;
* drawer mobile aberto;
* hover;
* foco.

Antes de criar novo armazenamento:

* auditar se o projeto já possui mecanismo para isso;
* reutilizar o mecanismo existente quando adequado;
* não criar migration sem necessidade;
* caso seja usado armazenamento local, atualizar a auditoria correspondente em `docs/privacidade/cookies.md`.

A ausência de armazenamento não pode quebrar o menu. O padrão seguro deve ser menu expandido no desktop e fechado no mobile.

## Acessibilidade

Garantir:

* navegação semântica;
* botões reais para grupos e controles;
* links reais para destinos;
* `aria-expanded`;
* `aria-controls`;
* `aria-current="page"` no link ativo;
* foco visível;
* funcionamento por teclado;
* Escape no drawer;
* retorno de foco;
* submenus fechados fora do fluxo de Tab;
* tooltips acessíveis;

Validar o shell com:
